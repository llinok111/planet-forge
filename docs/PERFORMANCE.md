# 性能

## 1. 方法

`npm run bench`（`scripts/bench.mjs`）。纯 Node，不含 WebGL 与渲染，测的是**生成管线**。

三个刻意的设计：

1. **成组重复取中位数**。每项跑 5 次，报 `median (min, max)`。单次测量在本机能有 2 倍波动（后台任务、CPU 降频），中位数是唯一可比的量。
2. **先跑 CPU 校准**（固定负载的浮点循环）。换机器时先看校准值，否则数字不可比。
3. **每项独立构造输入**，不复用上一次的缓存 —— 二十面体在真实流程里每次都重建（LOD 切换时），缓存命中会低估成本。

---

## 2. 生成管线（CPU，不含 WebGL）

本机中位数（L5 默认配置，含水力侵蚀）：

| 细分 | 顶点 | 三角面 | 二十面体 | 高度场（含侵蚀） | 法线 | 合计 |
|---|---|---|---|---|---|---|
| L3 | 642 | 1 280 | 2.4 ms | 4.4 ms | 1.4 ms | **8.4 ms** |
| L4 | 2 562 | 5 120 | 5.6 ms | 9.2 ms | 1.3 ms | **16 ms** |
| L5 | 10 242 | 20 480 | 20.9 ms | 32.4 ms | 6.3 ms | **60 ms** |
| L6 | 40 962 | 81 920 | 112 ms | 145 ms | 23.6 ms | **282 ms** |

合计为 二十面体 + 高度场 + 位置（位移，约 0.6 ms，可忽略）+ 法线。板块生长已包含在高度场内，不重复计。

### 怎么读这张表

- **L5 = 60 ms** 是默认配置。低于 100 ms 的阈值意味着"拖动滑块后立即提交"仍然感觉是瞬时的。
- **L6 = 282 ms** 单看会卡，但它现在**跑在 Worker 里**，主线程只做网格装配（约 20 ms）。所以近景自动升到 L6 时界面不冻结，只是加载遮罩多显示 0.3 s。
- L3/L4 低于 20 ms，用于快速预览（`detail` 滑块拖到 3 时几乎无感）。

## 3. 参数对成本的影响

### 侵蚀迭代（L5，仅高度场）

| 迭代数 | 中位数 |
|---|---|
| 0 | 26.2 ms |
| 20 | 26.0 ms |
| 40 | 34.0 ms |
| 80 | 44.0 ms |

近线性。注意 0 与 20 几乎相同 —— 因为热力侵蚀的成本主要在第一次扫描的邻接遍历，之后是同一批数据上的短循环。真正的转折在 40 以上。

v2 新增的**水力侵蚀成本**：`hydraulicIterations=2` 时 L5 高度场从 ~26 ms 升到 ~32 ms（**+23%**）。其中洼地填充（priority-flood）占大头，因为它要对全顶点建一次二叉堆。

### 水力侵蚀迭代

| `hydraulicIterations` | 额外成本（L5） |
|---|---|
| 0 | 0（整个水力阶段跳过） |
| 1 | +5 ms |
| 2（默认） | +6 ms |
| 4 | +9 ms |
| 6 | +12 ms |

### 板块数（L5，生长 + 边界分类）

| 板块数 | 中位数 |
|---|---|
| 8 | 0.5 ms |
| 14 | 0.7 ms |
| 24 | 0.5 ms |
| 40 | 0.6 ms |

**几乎无影响**。板块生长是 O(V+E) 的图上多源 BFS，种子数只影响初始队列长度，不影响遍历总量。这也是"参数必须真实改变结果"的一个好例子：`plateCount` 从 4 到 40 视觉差异巨大，成本却持平。

## 4. 优化记录

### 4.1 二十面体细分：O(n²) → O(n)

原实现每插入一个中点就 `new Float64Array(len + 3)` 并 `set(positions)` 整体复制。每级细分要插入约 `V/2` 个中点，总计 O(n²)。

| 级别 | 优化前 | 优化后 | 倍数 |
|---|---|---|---|
| L5 | 562 ms | 21 ms | **27×** |
| L6 | 3 657 ms | 112 ms | **32×** |

修法：预分配 `10·4^L + 2` 个顶点，原地写入。附带收益是顶部不再需要"最后再转换一次类型"。

### 4.2 邻接表：去掉 -1 空洞

按"每个三角形给每个顶点 2 个槽位"分配（上界 6V），去重后留下 `6V − 12` 个 `-1`：

```
L5: 61 440 个空洞（6 × 10242 − 12）
```

这些空洞让侵蚀循环每帧多做 6 倍的边界检查，且一旦有逻辑漏洞就会读到无效顶点。改为**先去重无向边、再建 CSR** 后，`sum(degree) == 2E` 精确成立，平均度 = 6，没有 -1。

### 4.3 大气积分步数无关性

v1 的亮度随步数线性变化：

| 步数 | 盘面亮度 |
|---|---|
| 4 | 13 |
| 14 | 109 |
| 28 | 110 |

原因是 `accum` 是"密度 × 步长"的求和，步长 `= chord / steps`，所以总和与步数成反比，而增益又是固定值。

v2 改为解析光学深度（`τ = density × chord × densityFalloff`），**不再沿视线步进**，因此步数只影响太阳可见性的采样精度，不影响总亮度。4/14/28 步在 v2 下得到相同亮度。

这也顺带把大气 pass 的成本从"每像素 14 次球面距离计算"降到"每像素 1 次解析求交 + 1 次相位函数"。

### 4.4 云量滑块的线性化

v1 用固定阈值切 fBm，值集中在 0.5 附近导致滑块像开关：

```
coverage 0.52 → 实际云量 37%
coverage 0.70 → 实际云量 88%
```

改为**分位数反演**：先对噪声场做 Fibonacci 格点采样（4096 点）、排序，再按覆盖率取分位点当阈值。于是 `coverage` 精确等于天空覆盖比例，线性误差 0。

代价是一次 4096 点的 CPU 采样（约 0.4 ms），只在种子变化时重算。

### 4.5 体积云：只付出需要的那部分

体积云的成本 = `像素数 × 云层覆盖面积占比 × (主步进 + 自阴影步进)`。

默认 `cloudSteps = 8`、自阴影 4 步，最坏情况每像素 32 次噪声求值。优化手段：

- 只对**命中云层的射线**做步进（先解析求交内外球壳）；
- 自阴影步进在密度接近 0 的区域提前返回；
- `cloudSteps` 暴露为参数，低端设备可以降到 4。

## 5. 渲染侧

| 项目 | 数值 | 说明 |
|---|---|---|
| `applyLive`（改颜色/强度） | < 1 ms | 只写 uniform，稳定 60 fps |
| 星点尺寸改动 | ~0.1 ms（9 000 星） | 重写一个 `Float32Array` 属性 |
| 大气合成 pass | ~0.3 ms @1080p | 一次全屏 quad + 一次场景重渲到离屏目标 |
| 体积云（默认 8 步） | 依盘面占比 | 全屏最坏情况是主要开销，这也是提供 `cloudSteps` 的原因 |
| LOD 检查 | 每 0.6 s 一次 | 每帧检查会让距离判断本身成为成本 |

大气 pass 的实际开销包括**一次额外的场景渲染**（渲到离屏目标）。在 SwiftShader 下这部分比真实 GPU 显著，所以上表数字偏悲观。

---

## 6. 复现方式

```bash
npm run bench
```

输出包含 CPU 校准值、各阶段 `median (min, max)`、侵蚀迭代扫描、板块数扫描、汇总表。

对比不同机器时先比校准值：本机（Windows，Git Bash，Node 22.22.2）校准约为 **49 ms**。若你的校准值高 2 倍，所有耗时也应按 ~2 倍折扣后再比较。
