# 限制与取舍

如实记录做不到的事、为什么做不到、以及代价是什么。每条都尽量给实测证据，而不是"可能有局限"这种没有信息量的话。

---

## 1. 导出

### 1.1 云、大气、星空不进入 GLB

**现象**：导出的 GLB 里只有位移地形与行星环，没有云、大气、星空。

**原因**：这三者的外观完全由运行时着色器决定 —— 体积云要逐像素步进、大气要做屏幕空间合成（依赖离屏渲染目标与深度）、星空是点云着色器。glTF 没有表达"任意 GLSL 程序"的机制，把它们烘成贴图会产生一张假图，反而误导使用者以为那是可复现的几何。

**代价**：场景 JSON 里记录了全部参数，在 Blender 里重新实现需要自行编写材质。

**为什么不烘贴图**：本项目的主张是"不是贴图球"。导出一个假贴图会直接违背这条主张。

### 1.2 GLB 顶点色是近似

导出时顶点色由 CPU 按与着色器**相同**的分带逻辑计算（高度 + 坡度 + 纬度 → 九段色带），但：

- 微纹理（`detailStrength`）、沉积物、水系染色**不烘焙** —— 它们是逐像素的高频调制，烘到顶点上会产生摩尔纹。
- 结果是导出模型看起来比画面里"干净一些"。

### 1.3 导出不含层级动画

GLB 导出静态帧。自转、云漂移、波浪都不导出。这是刻意的：把动画导进 glTF 需要关键帧采样，体积会涨 10 倍以上，而这套系统的主要用途是得到一颗可以进 DCC 处理的**几何体**。

## 2. 渲染

### 2.1 大气是单次散射 + 多次散射近似

v2 已经是屏幕空间合成的物理散射（解析光学深度、瑞利 `1/λ⁴`、Cornette-Shanks 米氏相函数），但仍不是辐射传输方程的完整解：

| 简化 | 后果 |
|---|---|
| 多次散射用各向同性的衰减回波代替 | 厚大气（`atmoDensity` 很低时）会比真实情况暗 —— 真实大气里高阶散射会把光"绕"到阴影区 |
| 暮光带宽度是经验常数 | 晨昏过渡带的宽度不随大气高度变化，物理上它应该随标高变化 |
| 没有行星表面到大气的光路耦合 | 明亮的雪原不会把大气的背光侧照亮（真实地球有这一项） |
| 太阳可见性用 `smoothstep` 而非解析球体遮挡 | 晨昏线是一个柔化带，不是精确的几何遮挡 |

**为什么不做完整版**：那需要预计算透射率 LUT（Hillaire 方案），首帧成本约 1–3 s，且要在 GPU 上生成 32×128×32 的 3D 纹理。对"拖滑块即时反馈"的交互目标不划算。

### 2.2 行星环是零厚度圆环

环粒子的垂直厚度未建模。边缘视角（`ringTilt` 接近 0）下环面完全平整 —— 真实环带在掠射角会呈现明显的厚度与自身遮挡。

**影响范围**：只在极小倾角时可见。`ringTilt` 默认 16°，此角度下不明显。

### 2.3 云层在两极有轻微拉伸

体积云的密度场在**局部空间**（球面方向 × 高度）采样，靠近极点时球面方向的采样密度会因为参数化的挤压而略微不均。`cloudBanding` 参数掩盖了大部分 —— 极区云量本来就应该少。

### 2.4 LOD 是两档切换，不是连续细分

**已改善（v2）**：从"无 LOD"变成"相机距离自动切换 L5/L6"，带 10% 迟滞带。

**仍存在的限制**：这是整球级别的切换，不是 quadtree / clipmap 那种只细化可见区域的方案。所以：

- 切换瞬间会有一次完整重建（在 Worker 里，不阻塞渲染，但加载遮罩会闪一下）。
- 近景看局部时，L6 的 40 962 顶点摊到整个球面上，局部密度仍然有限。真正的"贴地视角"需要 cubesphere 分块 LOD，那是另一个量级的工程。

### 2.5 软件渲染下的视觉基线

截图在 SwiftShader（CPU 光栅化）下拍摄，抗锯齿与各向异性过滤质量低于真实 GPU。真实设备上边缘会更干净，云层细节会更清晰。

**这条很重要**：不要把仓库里的截图当成"这个项目的最佳效果"。

## 3. 地形

### 3.1 水力侵蚀是简化版

**已改善（v2）**：加入了 priority-flood 洼地填充 + 流量累积 + 河道下切，能形成树枝状排水网。

**仍缺的**：

| 缺什么 | 后果 |
|---|---|
| 沉积 / 搬运 / 泥沙输运 | 不会形成冲积扇、三角洲、河漫滩 |
| 侵蚀-沉积耦合迭代 | 河道只下切不填，长期迭代会让地形过度"沟壑化" |
| 降雨的空间变化 | 全星球均匀降雨，因此水系密度在各纬度相同（真实行星赤道多雨、副热带干旱） |
| 湖泊 | 洼地被填平，形成不蓄水的平地，而不是湖面 |

`hydraulicIterations` 默认只有 2，就是因为在缺沉积项的情况下，迭代越多地形越像被刮过。

### 3.2 板块是 Voronoi 近似

板块生长是多源 BFS（图上最短路径），本质上是球面 Voronoi 的离散近似。真实板块形状由地幔对流决定，没有"面积均衡"这回事。本项目的面积均衡（最大/最小 < 4×）是为了视觉可读性 —— 一个占据半个星球的板块会让其余部分全是碎屑。

### 3.3 海平面是分位数，不是物理平衡

`continentBias` 直接指定"多少比例的表面在海平面以上"，然后反解海平面高度。真实行星的海平面由水量与洋盆容积平衡决定。

**取舍原因**：物理模型下 `continentBias` 这个滑块就不存在了 —— 用户只能调"水量"，而水和地形的关系是间接的。分位数方案让"我要 30% 陆地"这个意图可以精确表达，误差 < 0.01%。

### 3.4 高度场归一化的副作用

为了让 `mountainHeight` 等参数的 UI 值有实际意义，高度场在叠加细节后被缩放到 `plateHeight + mountainHeight + detailAmplitude` 的预算内。

副作用：**改小 `mountainHeight` 会让海底也变浅**，因为缩放是全局的。想要"陡峭陆地 + 深海"需要同时调 `continentBias`。

### 3.5 侵蚀会让某些参数相互耦合

热力侵蚀与水力侵蚀都在改高度，所以：

- `mountainHeight` 调高 ≠ 山峰等比变高（侵蚀会削掉一部分）
- `erosionIterations` 调高会让 `relief` 下降，但也会让 `continentBias` 的精度变差（已由二次重锚补偿）

这些耦合是物理正确的（真实地形也这样），但意味着参数不是正交的。

## 4. 工程

### 4.1 Worker 不可用时的回落路径

生成管线在 Web Worker 里跑。若环境不支持（老浏览器、某些 iframe 沙箱、`file://` 直接打开），会回落到主线程：

- 结果**完全一致**（同一份 `generateTerrain`）。
- 但 L6 的 282 ms 会阻塞主线程，拖动滑块时会卡。

HUD 的"生成线程"一栏显示当前走的是哪条路径。

### 4.2 参数面板不是通用的

面板由 `params.js` 的 schema 生成，支持 `range` / `toggle` / `color` / `seed` 四种类型。文本输入、下拉、分组折叠都没有实现。新增参数类型需要改 `ui.js`。

### 4.3 URL 长度无上限

全部 92 个参数都偏离默认值时，URL 约 1.2 KB。主流浏览器的实际上限在 2 KB 到 8 KB 之间，理论上安全，但没有做压缩或短链。

### 4.4 移动端只做了不溢出

375 px 视口下无横向滚动（有 e2e 断言），但参数面板在手机上需要滚动很长。没有做抽屉式折叠或手势适配。

### 4.5 渲染入口唯一

必须调 `planet.renderInto(renderer)`，不能直接 `renderer.render(...)`。后者会跳过大气合成 pass，画面失去空气感且**不会报错**。

这是 API 设计上的一个陷阱，没有运行时断言保护（只有在 reviewer 忘记时才暴露）。已写入 `docs/ARCHITECTURE.md` 和代码注释。

## 5. 测试手段的局限

### 5.1 视觉验收是像素测量，不是人眼

本环境的读图工具无法接收图像，因此画面验收以**定量测量**表达：

```
盘面与深空背景可区分       |mean − sky| > 6
边缘存在大气辉光           峰值 > sky + 5
昼夜明暗差                 > 10
arid / ocean 预设色调相反   R−B 符号相反
L6 近景方差 ≥ L5 中景
```

**能证明的**：元素存在、强度足够、参数真的生效、构图元素之间可区分。
**不能证明的**：好看不好看、构图是否舒服、色带过渡是否自然、有没有"诡异感"。

这是真实的能力缺口，不是谦虚。7 张截图已随仓库提供，最终审美判断需要人来看。

### 5.2 软件渲染是性能基线，不是性能结论

`npm run bench` 测的是 Node 侧生成（不含 WebGL），这部分结论可靠。但渲染侧的数字来自 SwiftShader，与真实 GPU 没有可比性 —— 所以渲染侧只报"相对关系"（大气 pass 增加一次全屏渲染），不报绝对帧率。

### 5.3 e2e 依赖 dev server

`npm run test:e2e` 需要先起 `npm run dev`。没有做自动拉起，因为在 CI 里进程管理更容易出错。生产产物的验证靠 `BASE_URL` 环境变量指向 `vite preview`。

### 5.4 静态守卫覆盖不全

三条守卫（uniform 双向核对、保留字、反引号）只覆盖**已经踩过的坑**。没有覆盖的包括：

- GLSL 中的精度声明缺失
- 采样器与纹理格式不匹配
- uniform 名称拼写错误（JS 有、GLSL 有，但传给 shader 时用错 key）

最后一条尤其隐蔽 —— 双向核对会通过，因为两边都有声明，但 `shader.uniforms.uFoo = uniforms.uBar` 这种接错仍然无法检出。

## 6. 有意不做的事

| 没做 | 原因 |
|---|---|
| 贴图烘焙 / PBR 贴图导出 | 与"不是贴图球"的主张冲突 |
| Cubesphere 分块 LOD | 工程量大一个数量级，且需要重构整个几何管线 |
| 大气透射率 LUT 预计算 | 首帧成本 1–3 s，破坏交互手感 |
| 地形侵蚀的泥沙输运 | 需要多层状态场（水量/泥沙/沉积），成本远超收益 |
| 行星环的粒子系统 | 视觉收益小，性能代价大（要百万级粒子才有体积感） |
| 多星球 / 星系 | 超出"单颗星球生成器"的范围 |
| 保存/加载工程文件 | URL 已经是完整状态，JSON 导出也能存 |
