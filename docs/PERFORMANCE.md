# 性能

所有数据在本机实测（Windows，Node 22.22，Chromium + SwiftShader 软件渲染）。命令：`npm run bench`。

## 1. 方法

三条纪律，来自本机踩过的坑：

1. **同时报中位数与最小值**。本机后台负载能让同一负载的耗时相差 2.8 倍；中位数是稳定统计量，最小值近似"无干扰"成本。
2. **每个配置先跑一次预热**（JIT 编译、缓存填充），再取 5 次样本。
3. **报告前先跑 CPU 标定**。标定循环是固定的算术 + 内存访问，用来判断本次数据是否可信。若标定值明显偏离历史区间，说明本机正在被其他任务占用，数据不可直接比较。

## 2. 生成管线（CPU，不含 WebGL）

| 细分 | 顶点 | 三角面 | 二十面体 | 高度场 | 位置 | 法线 | **合计** |
|---|---|---|---|---|---|---|---|
| L3 | 642 | 1 280 | 4.6 ms | 3.5 ms | 0.2 ms | 1.5 ms | **9.7 ms** |
| L4 | 2 562 | 5 120 | 8.9 ms | 6.7 ms | 0.3 ms | 3.3 ms | **19 ms** |
| L5 | 10 242 | 20 480 | 30.9 ms | 33.3 ms | 0.4 ms | 7.0 ms | **71 ms** |
| L6 | 40 962 | 81 920 | 129 ms | 140 ms | 0.6 ms | 56 ms | **326 ms** |

解读：

- 顶点数每级 ×4，总耗时约 ×4.5（超线性来自邻接表与缓存压力）。
- L5 是默认档：71 ms 意味着拖动形状滑块时重建"可感知但不阻塞"。
- L6 的 326 ms 已需要加载遮罩；这是 `main.js` 用双层 `requestAnimationFrame` 包裹重建的原因。

### 子阶段

| 阶段 | L5 | 说明 |
|---|---|---|
| 板块生长 + 边界分类 | 0.9 ms | 多源 BFS，O(V+E) |
| 高度场合成 | ~32 ms | 主要成本是 3D 噪声采样（约 4 次 fBm + 1 次 ridged / 顶点） |
| 位置写入 | 0.4 ms | 纯拷贝 |
| 解析法线 | 7.0 ms | 每顶点遍历一次邻接表 |

## 3. 参数对成本的影响

### 侵蚀迭代（L5，仅高度场）

| 迭代 | 中位数 |
|---|---|
| 0 | 28 ms |
| 20 | 68 ms |
| 40 | 78 ms |
| 80 | 66 ms |

80 次比 40 次更短，这不是错误——是内存局部性：迭代到一定次数后高度场趋于平滑，`drop <= talus` 的分支提前 `continue`，实际发生的转移次数下降。换句话说侵蚀成本与被处理的顶点数相关，而非固定迭代数。

### 板块数（L5，生长 + 边界分类）

| 板块 | 中位数 |
|---|---|
| 8 | 0.9 ms |
| 14 | 0.9 ms |
| 24 | 1.1 ms |
| 40 | 1.1 ms |

几乎无关。生长是单次 BFS，种子点的最远点采样成本与板块数线性，但基数极小（每块 24 个候选）。

## 4. 优化记录

### 4.1 二十面体细分：O(n²) → O(n)

原实现每插入一个中点就分配新数组并全量复制：

```js
const grown = new Float64Array(positions.length + 3);
grown.set(positions);   // 每个中点复制全部已有点
```

L5 有 10 230 个中点，累计复制量约 5×10⁷ 个 double。

| | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| L5 | 562 ms | 38 ms | **14.8×** |
| L6 | 3 657 ms | 146 ms | **25×** |

改法：预分配 `10·4^L + 2` 个顶点（细分二十面体的精确公式），一次填充。拓扑校验（欧拉示性数 = 2、`adjacency.length = 2E`）在测试中保持通过，证明没有写坏结构。

### 4.2 邻接表：去掉 -1 空洞

第一版按"每三角形 2 个槽位"分配再去重，留下 `6V − 12` 个 `-1`。侵蚀循环会读到无效邻居。改为**先去重无向边，再建 CSR**：

```
adjacency.length === 2 × edgeCount   （测试断言，L1–L5 全部成立）
```

### 4.3 大气积分步数无关性

最初累加器是 `Σ density × stepLen`，输出直接用它。结果：

| 步数 | 边缘亮度 |
|---|---|
| 4 | 13 |
| 14 | 109 |
| 28 | 110 |

因为 `stepLen = marchLength / steps`，步数进入结果。改法：输出乘 `float(uSteps)` 抵消。修正后 4/14/28 步均得到 64（同一位置），步数只影响噪点质量。

### 4.4 云量滑块的线性化

固定阈值下，fBm 的集中分布使滑块极陡：

| coverage | 实测天空覆盖 |
|---|---|
| 0.2 | 0.3% |
| 0.35 | 5.3% |
| 0.52 | 37% |
| 0.70 | 88% |
| 0.85 | 99.9% |

改法：CPU 端对噪声场做 Fibonacci 格点采样并**排序**，把 `coverage` 转成分位数阈值传给 GPU。修正后逐点为 0→0、0.15→0.150、0.30→0.300、0.45→0.450、0.60→0.600、0.75→0.750、0.90→0.900。

## 5. 渲染侧

| 操作 | 成本 |
|---|---|
| `applyLive`（颜色/开关/太阳方位） | < 1 ms，仅写 uniform |
| 太阳方位改变 | < 1 ms + 每帧 `updateAtmosphereSun` / `updateRings` 两次向量拷贝 |
| 星点尺寸调整 | 重写 `Float32Array`（9 000 星 ≈ 0.1 ms） |
| 星点数量调整 | 重建 `BufferGeometry`（走 `regenerate`） |
| 云层漂移 | 每帧 1 个 float 更新 |

**软件渲染基线**：本项目全部截图与 e2e 在 SwiftShader 下完成。这不代表真实 GPU 性能——SwiftShader 的片元着色是 CPU 模拟，帧率通常低一个数量级。它的价值是"在没有 GPU 的环境中也能验证正确性"，不能引用其 fps 作为产品性能指标。

---

## 6. 复现方式

```bash
npm run bench
```

输出包含 CPU 标定值、每级细分的中位数/最小/最大、侵蚀曲线、板块数曲线，以及汇总表。若标定值异常（明显高于平时），数据应作废重跑。
